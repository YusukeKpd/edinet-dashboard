# EDINET財務ダッシュボード 仕様書 v1.0

> 目的：上場企業の財務データを EDINET API から取得・蓄積し、**スクリーニング**と**企業比較**ができるダッシュボードを自作する。
> 実装は Claude Code で行う。本書はその仕様（要件・設計・タスク）をまとめたもの。

---

## 1. 決定事項サマリ

| 項目 | 決定内容 |
|---|---|
| データソース | EDINET API v2（書類一覧API＋書類取得API `type=5` CSV） |
| 対象書類 | 有価証券報告書(120)、訂正有報(130)、半期報告書(160) |
| 対象範囲 | 全上場企業 × 過去5期（MVP） |
| 言語 | Python 3.11+（パッケージ管理：uv） |
| DB / 保存形式 | DuckDB（処理用）＋ Parquet（配布用） |
| データ置き場 | GitHub Releases（タグ `data-latest` の添付ファイル） |
| ダッシュボード | Streamlit + Plotly（Streamlit Community Cloud） |
| 更新頻度 | **週1回 自動更新**（毎週月曜 6:00 JST） |
| 手動更新 | Streamlit の「今すぐ更新」ボタン → GitHub Actions を起動（ETLはActions側で実行） |
| 株価系指標 | MVP対象外（将来 J-Quants 等で拡張） |

## 2. システム構成

```
┌──────────────────────── GitHub Actions ────────────────────────┐
│ trigger: schedule(週1) / workflow_dispatch(手動)                  │
│                                                                  │
│  前回データDL(Releases) → ①取得 → ②パース → ③整形・指標計算     │
│                                  → Parquet出力 → Releasesへ上書き │
└──────────────────────────────────────────────────────────────────┘
          ▲ workflow_dispatch (GitHub API)          │ Parquet
          │                                         ▼
┌──────────────────────── Streamlit ─────────────────────────────┐
│  起動時 / キャッシュ切れ時に Releases から Parquet を取得 → DuckDBで読込 │
│  スクリーニング / 企業比較 / 企業詳細 / 業種分析 / 更新ボタン         │
└──────────────────────────────────────────────────────────────────┘
```

- **重い処理はすべて Actions**。Streamlit は表示専用（読み取りのみ）。
- Streamlit Cloud のファイルシステムは揮発するため、データの正は Releases に置く。

## 3. データ取得（EDINET API v2）

### 3.1 事前準備
- EDINET で API キーを発行 → GitHub Secrets `EDINET_API_KEY`
- EDINETコードリスト（CSV）→ `companies` の元データ

### 3.2 エンドポイント
| 用途 | リクエスト |
|---|---|
| 書類一覧 | `GET https://api.edinet-fsa.go.jp/api/v2/documents.json?date=YYYY-MM-DD&type=2&Subscription-Key=...` |
| 書類取得 | `GET https://api.edinet-fsa.go.jp/api/v2/documents/{docID}?type=5&Subscription-Key=...`（XBRL→CSVのZIP） |

### 3.3 取得ルール
- リクエスト間隔 **1秒以上**、失敗時は指数バックオフで最大3回リトライ
- 取得済み docID はスキップ（冪等）
- 差分範囲：`etl_log` の「最終取得日の翌日 〜 今日」＋ **直近7日を再取得**（取下げ `withdrawalStatus`・訂正の拾い漏れ対策）
- CSV は **UTF-16 / タブ区切り**
- 初回のみバックフィル（過去5年分、ローカル or 手動実行のActionsで分割実行）

## 4. データモデル

### 4.1 テーブル
```sql
CREATE TABLE companies (            -- 企業マスタ（月1でコードリスト再取込）
  edinet_code TEXT PRIMARY KEY, sec_code TEXT, name TEXT,
  industry TEXT, fiscal_month INT, listed BOOLEAN
);

CREATE TABLE documents (            -- 書類メタ
  doc_id TEXT PRIMARY KEY, edinet_code TEXT, doc_type_code TEXT,
  period_start DATE, period_end DATE, submit_datetime TIMESTAMP,
  accounting_standard TEXT,         -- JGAAP / IFRS / USGAAP
  withdrawn BOOLEAN, downloaded BOOLEAN, parsed BOOLEAN
);

CREATE TABLE facts (                -- 縦持ち生データ（標準タクソノミ要素のみ保存）
  doc_id TEXT, element_id TEXT, context_id TEXT,
  unit TEXT, value DOUBLE, consolidated BOOLEAN, period TEXT
);

CREATE TABLE financials (           -- 横持ち（1社・1期・連結/単体で1行）
  edinet_code TEXT, fiscal_year INT, period_end DATE, period_months INT,
  consolidated BOOLEAN, doc_type TEXT,          -- annual / semiannual
  revenue DOUBLE, operating_income DOUBLE, ordinary_income DOUBLE, net_income DOUBLE,
  total_assets DOUBLE, net_assets DOUBLE, equity DOUBLE,
  interest_bearing_debt DOUBLE, cash DOUBLE,
  cfo DOUBLE, cfi DOUBLE, cff DOUBLE,
  eps DOUBLE, bps DOUBLE, dividend_per_share DOUBLE,
  employees INT, shares_outstanding DOUBLE,
  source_doc_id TEXT,
  PRIMARY KEY (edinet_code, fiscal_year, consolidated, doc_type)
);

CREATE TABLE etl_log (              -- 実行ログ
  run_id TEXT, started_at TIMESTAMP, finished_at TIMESTAMP,
  date_from DATE, date_to DATE, docs_fetched INT, docs_failed INT,
  status TEXT, message TEXT
);
```

### 4.2 勘定科目マッピング（`mapping.yaml`）
- 標準項目 → 候補要素IDの**優先順リスト**。先頭から探して最初に見つかった値を採用
- 優先度：①「主要な経営指標等の推移」要素（`*SummaryOfBusinessResults`、IFRS版含む）→ ②本表要素（`jppfs_cor:*` / `jpigp_cor:*`）
- コンテキスト：`CurrentYearDuration` / `CurrentYearInstant` / `Prior{n}Year*`。`_NonConsolidatedMember` 付きは単体。**連結優先、なければ単体**
- 訂正報告書(130)は同期間の値を上書き。取下げ書類は除外
- 金融業（銀行・保険・証券）は営業利益等の欠損を許容し、`industry` で表示を切替

```yaml
revenue:
  - jpcrp_cor:NetSalesSummaryOfBusinessResults
  - jpcrp_cor:RevenueIFRSSummaryOfBusinessResults
  - jpcrp_cor:OperatingRevenue1SummaryOfBusinessResults
  - jppfs_cor:NetSales
operating_income:
  - jppfs_cor:OperatingIncome
  - jpigp_cor:OperatingProfitLossIFRS
```

### 4.3 配布ファイル（Releases `data-latest`）
| ファイル | 内容 | 用途 |
|---|---|---|
| `companies.parquet` | 企業マスタ | Streamlit |
| `metrics.parquet` | financials＋計算済み指標 | Streamlit |
| `documents.parquet` | 書類メタ | ETL差分判定 |
| `facts.parquet` | 縦持ち生データ | ETL再構築 |
| `etl_log.parquet` | 実行ログ | 最終更新日表示・差分起点 |

## 5. 指標定義（`metrics`）

| カテゴリ | 指標 | 定義 |
|---|---|---|
| 成長性 | 売上高成長率 | revenue / 前期revenue − 1 |
| | 営業利益成長率 / EPS成長率 | 同上 |
| | 売上3年・5年CAGR | (revenue / n年前)^(1/n) − 1 |
| 収益性 | 営業利益率 / 経常利益率 / 純利益率 | 各利益 / revenue |
| | ROE | net_income / 期首期末平均equity |
| | ROA | net_income / 期首期末平均total_assets |
| 安全性 | 自己資本比率 | equity / total_assets |
| | D/Eレシオ | interest_bearing_debt / equity |
| | ネットキャッシュ | cash − interest_bearing_debt |
| CF | FCF / FCFマージン | cfo + cfi / ÷ revenue |
| | 営業CFマージン | cfo / revenue |
| 効率性 | 総資産回転率 | revenue / total_assets |
| | 1人あたり売上・営業利益 | ÷ employees |
| 株主還元 | 配当性向 / DOE | DPS / EPS、配当総額 / equity |

- 成長率は `period_months = 12` 同士のみ計算（変則決算はNULL＋フラグ）
- 0割はNULL

## 6. ダッシュボード（Streamlit）

### 6.1 ページ
| ページ | 機能 |
|---|---|
| **スクリーニング** | サイドバーで業種・売上規模・各指標の範囲を指定 → ソート可能な表＋CSVダウンロード／散布図（X・Y・バブルサイズ・色を指標から選択） |
| **企業比較** | 社名・証券コード検索で最大5社選択 → 指標別の時系列折れ線、直近期レーダーチャート、横並び比較表 |
| **企業詳細** | 1社のPL/BS/CF推移、主要指標カード、業種中央値との比較 |
| **業種分析** | 業種別の指標分布（箱ひげ図）、業種内ランキング |
| **データ管理**（管理者） | 最終更新日時・直近実行ログ・項目充足率、**「今すぐ更新」ボタン** |

### 6.2 表示ルール
- 金額は百万円単位、比率は%表示（小数1桁）、欠損は「–」
- 連結／単体の切替トグル（デフォルト連結）
- 全ページ上部に「データ最終更新：YYYY-MM-DD」を表示

### 6.3 データ読込
- `@st.cache_data(ttl=86400)` で Releases から Parquet を取得し DuckDB（インメモリ）で読込
- 更新完了検知時に `st.cache_data.clear()`

## 7. データ更新

### 7.1 自動更新（GitHub Actions）
- `.github/workflows/update.yml`
- `schedule: cron: "0 21 * * 0"`（UTC日曜21:00 = **JST月曜6:00**）
- `workflow_dispatch` も有効化（手動起動用）
- `concurrency: group: etl, cancel-in-progress: false`（多重実行防止）
- `timeout-minutes: 120`（6月下旬の集中期を考慮）
- 1回あたりの処理書類数に上限（例：1,500件）。超過分は次回へ繰越
- 手順：Releasesから前回Parquet取得 → 差分取得 → パース → financials/metrics再計算 → Releases上書き → etl_log追記
- 失敗時は Actions の通知（メール）で検知

### 7.2 手動更新（Streamlitボタン）
- 「データ管理」ページに配置、**管理者パスワード入力後のみ表示**（`st.secrets["ADMIN_PASSWORD"]`）
- 押下 → GitHub REST API `POST /repos/{owner}/{repo}/actions/workflows/update.yml/dispatches` を呼ぶだけ（ETLはStreamlit内で実行しない）
- トークンは `st.secrets["GITHUB_TOKEN"]`（fine-grained、対象リポジトリの Actions: write のみ）
- 実行中は状態表示（Actions API で run status をポーリング）、完了後キャッシュクリア
- 実行中はボタン無効化

### 7.3 月次メンテ（同ワークフロー内で月初のみ実行）
- EDINETコードリスト再取込（新規上場・廃止・社名変更）
- 項目充足率レポートを生成し、マッピング漏れを確認

### 7.4 再構築
- `mapping.yaml` 変更時は `facts` から `financials` を再生成（APIは叩かない）。`workflow_dispatch` の入力 `rebuild=true` で実行

### CLAUDE.md に記載するルール
- APIキー・トークンはコミットしない（`.env` / Secrets）
- EDINET へのリクエスト間隔は1秒以上
- 取得済みデータを削除する処理を書かない（再構築は facts から）
- `mapping.yaml` を変更したら `tests/test_financials.py` を実行
- Streamlit 側で ETL を実行しない

## 10. 注意点・今後の拡張

**注意点**
- 勘定科目の揺れが最大の工数。充足率を見ながら mapping を段階的に追加する
- 四半期データは2024年4月以降、半期報告書のみ（四半期は決算短信＝TDnet）
- 変則決算は `period_months` で判別し成長率計算から除外
- Releases の添付ファイルは1ファイル2GBまで。`facts` が肥大化したら年別分割 or 外部ストレージ（Cloudflare R2 等）へ移行
- ザイマニのUI・デザインは複製せず、公開データから同等機能を自作する

**将来拡張**
- 株価連携（J-Quants）で PER / PBR / 配当利回り / EV/EBITDA
- 決算短信（TDnet）で四半期データ
- セグメント情報、テキスト情報（事業等のリスク等）の取込
- ウォッチリスト・スクリーニング条件の保存
